# 1.0.2 出口恢复优化与双机部署

北京时间 2026-10-24 深夜开始，测试延续到次日凌晨。用户授权优化启停/节点切换的等待、安装两台路由器，并同步源码和开发日志。以下只记录实际观测，不包含路由器公网入口、节点地址/凭据、SSH 身份或原始浏览日志。

## 修改依据

旧监管在前台执行健康探测，外部超时会延迟节点变化检测；启动依赖等待会退避到 60 秒，稳态周期、连续失败和 DNS 冷却可能进一步叠加。监听和防火墙存在只能证明接管建立，不能证明新的国外出口可用。

1.0.2 将健康探测后台化，启动初期缩短依赖退避，配置事件和内容变化进入恢复期，立即验证出口并快速重试。恢复期加密备用必须实测成功才能切换；核心/节点变化时旧结果作废。LuCI 分开显示核心运行和国外出口验证。用户操作可排在健康探测锁后，不再争抢或删除锁。

## 主机回归与交付检查

- 使用真实 Lua 5.1、由 SDK 构建的 nixio/jsonc、sing-box 1.12.25、Xray 25.2.21、私有 dnsmasq 2.93。
- 完整回归覆盖 SOCKS/Fake-IP、透明模式、VLESS/Reality/Vision、双栈 TCP/UDP、QUIC 策略、正式 fork 模式下 128 次混合 DNS，并验证 DNS-only 更新及绑定失败回退时同一 TCP 流保持。
- 新增恢复期首次失败/稳态连续失败、已验证备用、旧探测作废、相同大小/mtime 的节点内容变化、SOCKS 事件不重启和实际内核锁下用户任务排队。
- 目标 Lua 32 位整数格式差异在打包前修复，两架构包内模块与测试源码逐字节核对；检查私有 DNS ELF、执行权限、菜单及压缩后的 LuCI v2 行为。
- cortex-a53 / generic 分别使用对应 CPU 编译参数。没有替换任何共享 sing-box、Xray 或跨内核安装 kmod。

## MTK / BPi-R3 Mini

环境：ImmortalWrt 24.10-SNAPSHOT、kernel 6.6.127、aarch64_cortex-a53，系统 sing-box 1.12.22、Xray 25.2.21。**实际运行透明模式**，不是 SOCKS 模式。

从服务/UI 1.0.0-r1 升至 1.0.2-r1。升级前保存新旧 IPK、配置与持久数据，独立十分钟守护在未确认成功时自动回退；验证成功后解除守护并 hold 两个包。安装保留用户 conffile，生成 `flowdns-opkg` 提示属正常保留行为。

| 项目 | 本次观测 |
| --- | --- |
| 升级后状态 | running / egress_ready / attached 均为 true，错误为空 |
| 仅配置事件通知 | 约 2 秒完成出口验证，核心 PID 不变 |
| stop/start | 约 11 秒完成出口验证；不是断电冷启动测试 |
| 独立 SOCKS YouTube HTTPS | HTTP 200，首字节约 0.91 秒，总计约 2.68 秒 |
| 完整诊断 | 各项检查通过 |
| 真实切换到另一个已验证节点 | 从重启 SSR 开始计约 13 秒完成出口验证，随后 YouTube HTTP 200；SSR 重启本身占其中约 10 秒 |
| 结束状态 | 恢复原节点，FlowDNS/SSR/DHCP/SmartDNS/network/firewall 配置 SHA256 与升级前一致 |

第一轮真实切换测试误套用了 SOCKS 的“核心 PID 不变”断言，未将该轮当作通过。补加逐步记录、独立恢复守护后确认 MTK 透明模式需要重载独立 Xray，PID 改变是预期行为；完整复测请求成功并恢复原配置。仅节点事件不重启与真实节点变化重载，是不同测试条件。

## R5S / RK3568

环境：NanoPi R5S、自报 OpenWrt 24.10.2 / LEDE R25.8.8、kernel 6.12.41、aarch64_generic。实际运行 SOCKS 模式；保留私有 sing-box 1.12.25-r1 和原系统 1.11.15。

服务/UI 从 1.0.1-r1 升至 1.0.2-r1，同样使用独立超时回退、逐项摘要核对和成功后的包 hold。私有核心的 hold 保留。

| 项目 | 本次观测 |
| --- | --- |
| 升级后状态 | running / egress_ready / attached 均为 true，错误为空 |
| 仅配置事件通知 | 约 2 秒完成出口验证，核心 PID 不变 |
| stop/start | 约 7 秒完成出口验证 |
| 独立 SOCKS YouTube HTTPS | HTTP 200，首字节约 1.09 秒，总计约 3.45 秒 |
| 完整诊断 | 各项检查通过 |
| 客户端 DNS | 国内域名返回真实双栈地址，YouTube 返回预期 Fake-IP |
| 客户端经刚返回的 Fake-IP 发起 HTTPS | YouTube HTTP 200，首字节约 3.42 秒，总计约 6.58 秒 |
| 国内客户端 HTTPS | USTC HTTP 200，约 0.12 秒；腾讯首页另一次 HTTP 501 不作为连通成功项 |
| 真实切换到另一个已验证节点 | 从重启 SSR 开始计约 9 秒完成出口验证，FlowDNS 核心 PID 不变；随后 YouTube HTTP 200 |
| 结束状态 | 原节点恢复，全部六项配置 SHA256 与升级前一致 |

客户端 Linux 位于虚拟机 NAT 后；显式向 R5S 查询并使用其刚返回的 Fake-IP 进行请求。该测试验证 DNS/代理链路，不测浏览器缓存、播放器吞吐或完整公网 IPv6。

R5S 第一个备用节点在独立回环实例验证时超时，未切换生产；随后改用另一通过 HTTPS 验证的现有节点，才进行真实切换。该超时不作为 FlowDNS 恢复失败，也不将所有备用节点声明为可用。

## 恢复与范围

新旧包、私有配置和守护脚本保存在每台路由器的权限受限备份目录。公开仓库与源码归档只包含默认配置、程序、测试和整理后的证据。旧版发布与标签保留。

恢复期“约 2 秒”是探测调度间隔，不是任意节点两秒可用的承诺。SSR/PassWall 自身停止/启动、外部 DNS/TLS、线路故障、完整透明重载及客户端旧 DNS 缓存都可能增加时间。此次没有强制故障注入生产网络，没有重启路由器，没有进行持续大带宽或视频测速；完整隔离回归和现场烟测分别陈述。

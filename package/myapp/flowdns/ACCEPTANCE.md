# 真机恢复与稳定性验收

本文保留早期验收时间线；最新正式发布结果见 [1.0.0 发布记录](diagnostics/2026-10-23-1.0.0-release.md)。下文早期“尚未验收”按对应版本理解。

## 当前证据

用户的 ImmortalWrt ARM64 路由器使用 sing-box 1.12.22。用户已确认 YouTube 恢复；路由器 SOCKS HTTPS 请求返回 HTTP 200，状态页显示监听与接管就绪、正式核心 TCP/UDP DNS 探测通过。2026-10-20 用户进一步确认，路由器重启后程序自动启动且运行正常，重启自启动验收通过。断电冷启动、代理中断恢复、独立 IPv4/IPv6 和持续运行验收仍未完成。

此次附带的 `nslookup` 均在路由器 SSH 执行。QQ 返回真实 A/AAAA；Google 返回的地址不在 FlowDNS 的 `198.18.0.0/15`、`fc00::/18` Fake-IP 范围内。记录为路由器本机原有 DNS 路径的观测，不能当作 LAN 客户端分流或国外解析正确性的验证。

2026-10-20 用户随后从 Windows 电脑向 `192.168.10.1` 查询：QQ 返回真实 IPv4/IPv6 地址，Google 返回 `198.18.0.7`、`fc00::8`。这两项客户端 DNS 策略验证通过，并与用户报告的实际网页访问正常一致。用户说明当前没有公网 IPv6 环境；返回 AAAA Fake-IP 不代表公网 IPv6 连通，IPv6 访问仍未验收。

路由器 SSH 使用 Linux 命令，Windows 电脑 CMD 使用 `curl.exe`。路由器本机查询不经过 LAN 透明接管，不能用它代替电脑/手机的访问验证。

## 1. 准备

保持当前节点、DNS 和规则配置，先在“状态与排查”运行完整诊断，导出一次诊断报告。r3 增加“开机自启动”行，必须同时满足已注册开机服务和统一分流已启用，才能期待开机后接管。

在路由器 SSH 可以只读确认开机注册和配置：

```sh
/etc/init.d/flowdns enabled && echo '开机服务已注册'; uci -q get flowdns.main.enabled
```

预期看到“开机服务已注册”和 `1`。如未注册而需要开机启动，执行 `/etc/init.d/flowdns enable`。如开关为 `0`，通过 FlowDNS 设置页启用并保存应用。

## 2. 重启后恢复

当前记录：2026-10-20 用户已确认重启后自动启动、运行正常。后续版本可继续按以下方法复验；本次反馈未提供精确恢复耗时，未单独验证断电冷启动。

在可接受短暂断网时，通过 LuCI 的系统重启功能重启一次。网络恢复后打开 FlowDNS 状态页：

1. 可以先出现等待网络、时间或 SOCKS 的原因，随后应进入“运行中 / 监听就绪 / 已接管”。
2. 无需重新保存配置，电脑和手机应能访问国内站点及 YouTube。
3. 再运行完整诊断并导出报告，与重启前比较。记录从路由器可登录到分流恢复的实际时间；90 秒仅是每次核心加载等待上限，不是整台路由器的启动时间承诺。

若反复等待或失败，保留等待原因、启动日志及“近期错误”，不要反复更换 DNS/规则来掩盖故障。

## 3. 代理中断与恢复

从局域网管理路由器，在可接受国外连接中断时，临时停止所选代理插件的服务，再重新启动同一服务。保持原节点、FlowDNS 配置及规则不变。

停止期间预期：

- 国内 DNS 和国内站点仍可访问，FlowDNS 核心及接管保持运行。
- 国外访问失败；默认约 60 秒一次的健康探测会将状态改为部分链路异常。

重新启动代理插件后预期：

- SOCKS 恢复后，国外新连接能够恢复，无需重新保存 FlowDNS。
- 后续健康探测恢复正常。已有连接可能需要网页重试或应用重连。
- 节点本身无法连通时，不将其误判为 FlowDNS 必须自动切换节点；节点仍由代理插件管理。

记录中断和恢复时间，并在恢复后导出报告。

## 4. 电脑 IPv4 / IPv6 对照

在 **Windows 电脑 CMD** 执行以下完整一行；不要贴进路由器 SSH：

```bat
nslookup www.youtube.com 192.168.10.1 & curl.exe -4 -v -I --noproxy "*" --connect-timeout 10 --max-time 25 https://www.youtube.com/ & curl.exe -6 -v -I --noproxy "*" --connect-timeout 10 --max-time 25 https://www.youtube.com/
```

实际网关地址不同时替换 `192.168.10.1`。保留完整输出以区分 DNS、连接和 TLS 阶段。IPv6 测试还取决于电脑是否具有可用 IPv6 路由，单独失败需要先核对网络环境。最后用浏览器验证网页和视频播放；HTTPS 响应通过不等于所有视频 CDN 与 QUIC 已通过。

## 5. 持续使用

在不改节点/规则的情况下持续使用至少一小时，开始和结束分别运行完整诊断及 CPU/内存采样并导出报告。记录是否发生断流、核心反复重启、国内变慢、内存持续下降；性能比较使用 `tools/flowdns-benchmark.py`，固定同一节点和下载目标。

没有实际持续运行数据前，不标记长期稳定性通过。本文件不创建定时任务，也不自动重启路由器或代理插件。

## 6. 0.3 透明核心模式试用

按 README 的额外依赖和切换步骤操作。先在原 SOCKS 模式记录同节点、同视频的连接速度和 CPU/RSS，再切换透明核心模式，清理客户端 DNS 缓存并重开浏览器。国内/国外域名应均返回真实 IP；确认国内网站、国外网页和视频播放，比较持续下载与卡顿，不能仅凭 YouTube 单个瞬时数字判定。

验证 SSR 独立 SOCKS 切换到另一受支持节点后 FlowDNS 会校验重载；再切回。新节点失败时查看生成/检查错误，不自动认定代理线路可用。分别测试实际 UDP/QUIC、SSR SOCKS 暂停后的 DNS 恢复、重启、规则更新、DNS 备用切换；新模式重载会清空动态集合并断开旧连接，重查 DNS 后应恢复。共享 CDN IP 可能优先走代理，需结合规则查询和实际日志判断。

故障时先通过页面切回原 SOCKS 模式保存应用，清理客户端缓存，验证恢复。安装前保留 0.2.0-r3 服务与 0.2.0-r1 界面包。当前没有任何新模式真机吞吐或长期稳定性结论。

## 7. 0.3.1 修复验收

当前远程路由器继续使用用户选择的恢复方案。0.3.1 私有 DNS 与队列修复先完成本地验证；目标安装和透明模式切换安排在有本地恢复条件的维护窗口。升级服务和界面后，检查私有 DNS 2.93 是否可执行、生成配置测试、实际国内外访问；并发 TCP/UDP DNS 不应出现 nftset/netlink cache 错误或前端退出。连续保存应用、reload 与 LAN up 同时发生时应排队或明确拒绝重复操作，不能变成等待自身锁的 boot；故意失败的新配置应验证原模式恢复。保留 job、operation、recovery 和各核心日志，不删除工作锁文件。

2026-10-23 用户进一步授权远程部署、禁用冲突非核心服务并测试。已完成真实 LAN TCP/UDP A/AAAA DNS 128 次并发、国内 HTTPS、Google 204、YouTube 200；清理 SSR 遗留原生 nft 表前国外 443 被改写到停用的 1234 端口，清理后恢复。详见 diagnostics/2026-10-23-retest.md。此项不代替重启、实际视频、UDP/QUIC、IPv6 公网和长期稳定性验收。
